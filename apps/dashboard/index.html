What's built

Every capability below runs today — verified against live Bright Data infrastructure, not mocked.

01

Data contracts

One YAML per collector: field types, required fill rates, and a plain-language description of each field. That description doubles as the repair instruction.

02

Automatic breakage detection

Every run is scored 0–1. Catches null-fills, wrong types, unit drift, and row-count collapse — the failures that never throw an error.

03

Self-writing heal prompts

A failing score becomes the exact text handed to bdata scraper heal — worst field first, budgeted to the CLI's 1000-character limit.

04

The approval gate

The piece everyone skips. A proposed fix is re-scored against the same contract before it's saved, and rejected if it doesn't repair what broke or damages a healthy field. Proven live: a real heal was correctly refused.

05

Verification runs

Approving isn't trusting. After a fix lands, a fresh run must independently pass the contract before the outcome is called healed.

06

Append-only ledger

Every run, prompt, gate verdict, and outcome is logged and never edited. The audit trail answers "why did this collector change?"

07

Novelty diffing

Rows are matched by identity key across runs, so the system reports what's new or changed — not just whether it's still healthy.

08

Bootstrapped contracts

Ask about something nobody wrote a scraper for. The first successful run infers its own contract — types, required-ness and all — so it's self-healing from day one.

09

Freshness learning

A topic that never changes earns a longer re-check interval; one that moves fast earns a shorter one. Driven by real novelty history, not a fixed cron.

10

Cache-first value gate

Nothing reaches the network before the cache is checked. A repeat question is answered for free instead of spending a credit twice.

11

The Break Room

A target page we control, rendered from one dataset into two layouts. Flip it and a real redesign happens on demand — so healing is reproducible, not a story.

12

Unattended CI + Sentinel

Every push replays the full loop with no credentials. A nightly cron sweeps the real fleet, commits its ledger, and opens an issue if anything can't self-heal.

Radar — asked on demand

These weren't scheduled. Someone asked a plain-language question; the topic either served from cache for free or ran the same score → heal → gate → verify loop above, bootstrapping its own contract on the first ask instead of needing one written ahead of time.
